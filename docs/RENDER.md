## What the Blueprint creates

The root `render.yaml` defines one Docker web API on the free plan in Singapore,
from `develop`, with manual deployments and `/readyz` as its health check. The
server binds `0.0.0.0` and reads Render's supplied `PORT`. The image uses Node 22
and contains compiled API/worker code and committed migrations. It runs only
`dist/server.js`; it does not run a Docker Engine or start a worker. A reviewed
Docker context allowlist excludes `.env`, certificates, dependencies and local
mail from upload. No hosted database, Redis, paid service or mail account is
created by this Blueprint.

Free services sleep after inactivity and block SMTP ports. The existing Gmail
adapter is local-only and production startup rejects it regardless of plan.
Do not set development mode to bypass this check. See
[Render free service limits](https://render.com/docs/free).

## Before creating the service

1. Sign in to Render and connect the GitHub repository
   `Yoshi4489/cyber-lab-backend`, selecting `develop`.
2. Provision hosted PostgreSQL (Render or Neon) with a migration owner and a
   separate restricted application login. Use verified database TLS for public
   connections and the provider-approved connection configuration. Do not use
   the local demo URL, expose local PostgreSQL, or grant runtime table ownership.
3. With the owner credential available only to the migration process, run
   `node dist/db/migrate.js` from the built repository/image. Apply
   `scripts/db-app-role.sql` and verify the effective application privileges as
   described in [database roles](DATABASE_ROLES.md). Never put the owner URL in
   the API service. Do not automatically run migrations under the runtime login.
4. Configure Resend and verify a sender domain. Keep its API key backend-only.
   Production startup requires `MAIL_PROVIDER=resend`, `RESEND_API_KEY` and
   `EMAIL_FROM`. The Render HTTPS subdomain handles API TLS; it does not verify
   an email sending domain. No mail should be sent without recipient approval.
5. Build an isolated hosted demo database and provision fresh player/admin
   credentials through `node dist/db/seed.js` with private `SEED_*` variables.
   Remove seed passwords from the environment after the one-off command. This
   seeds catalog data and verified accounts without opening signup. Do not
   silently upload the existing local database or reuse its credentials.

## Blueprint and frontend settings

Create a Blueprint from `render.yaml`. Render prompts for the application
`DATABASE_URL`, Resend key/sender and service-token issuer/audience. Set issuer
and audience to match the frontend server (for example `cyber-range-frontend`
and `cyber-range-backend`). Three independent backend secrets are generated by
the Blueprint. Keep their values out of screenshots, chat, logs and Git.
See [Render Blueprint fields](https://render.com/docs/blueprint-spec).

After the API is healthy, set these **server-only** Vercel variables and redeploy
the frontend:

| Variable | Source |
|---|---|
| `BACKEND_URL` | Actual `https://...onrender.com` API URL |
| `BFF_AUTH_SECRET` | Same bootstrap key as API |
| `BACKEND_SERVICE_TOKEN_SECRET` | Same signing key as API |
| `SERVICE_TOKEN_ISSUER`, `SERVICE_TOKEN_AUDIENCE` | Same values as API |
| `BFF_SESSION_SECRET` | Independently generated frontend cookie sealing key |
| `BFF_PUBLIC_ORIGIN` | `https://cyber-lab-frontend.vercel.app` |

Never use `NEXT_PUBLIC_*` for credentials. Do not give the frontend
`DATABASE_URL`, Resend, Redis, flag-derivation or Docker secrets. Vercel team
access remains separately required for the protected frontend deployment.

## Worker and target routing

Hosting this API alone does not enable lab sessions. The worker must use the
same hosted database and flag key, have reachable authenticated Redis, and
reach the isolated target Engine over verified mTLS. Do not start a second
worker; concurrent workers are unsupported. The current VirtualBox private
addresses and loopback target URLs are not reachable by cloud services or
remote players. Provision reviewed worker networking and public HTTPS ingress;
configure `LAB_PUBLIC_BASE_URL` only after it works. Keep Docker credentials on
the worker and retain the existing isolation restrictions. Do not publicly
expose an unauthenticated Engine, Redis or database to solve reachability.
